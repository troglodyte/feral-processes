# Nemesis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** A wild program that beats the party, or that they bail out on,
keeps standing on the map with a name, a rarity promotion, a taunt for the
rematch, and two visual marks.

**Architecture:** Entity-bound. A new `Nemesis(u32)` component on the
surviving hostile, marked by one predicate inside `Game::end_battle` that
reuses the win test already there. Rarity promotion applies the *ratio*
between tiers rather than the tier, because the `Rarity` component is a
receipt for a multiplier already spent at spawn. Names and taunts come from
a `.ron` bank derived through `derive::index` — no RNG draw anywhere in the
feature.

**Tech Stack:** Rust, `bevy_ecs` 0.19 (standalone, engine only), `ron`,
`serde`. `crates/engine` and `crates/gui`.

**Spec:** `docs/superpowers/specs/2026-08-17-nemesis-design.md` — read it
first. This plan argues from it and does not restate its reasoning.

## Global Constraints

Every task's requirements implicitly include this section.

- **No `save::SAVE_FORMAT_VERSION` bump.** The payload is field-named RON
  since v29; an additive field behind `#[serde(default)]` loads out of older
  files. Bumping it is a plan failure, not a safety measure.
- **No `resources::GameRng` draw anywhere in this feature.** `end_battle`
  runs in every arena fight, so a draw shifts the stream for every scenario
  in `dev-arenas/`. Use `derive::index` over a hand-rolled fold.
- **Never `seed % pool.len()`.** `derive::index` is Lemire's high-bit
  reducer and exists so nobody writes `%` again. Read that module's doc.
- **Content is data.** Names and taunts are `.ron` files under
  `assets/nemesis/`. A malformed file is skipped with a logged warning,
  never a panic — follow `DescriptionDb::load_dir`
  (`crates/engine/src/descriptions.rs:182`). Update
  `assets/nemesis/README.md` in the same change as any schema change.
- **Tuning values go in `crates/engine/src/tuning.rs`** as documented `pub
  const`, never inline in a formula.
- **`cargo fmt` and `cargo clippy --workspace` after every change.** Fix
  warnings rather than silencing them.
- **`cargo test --workspace` is the gate.** A seeded engine test can pass
  under `-p feral-processes-engine` and fail under `--workspace` — they are
  different builds with different RNG streams. Iterate with `-p`, gate with
  `--workspace`.
- **Branch is `nemesis`. Commit freely at each green step. Do not push, and
  do not tag** — versioning happens once, at the merge.
- **Do not update `docs/manual.md` or the root `README.md`.** Both are
  carved out of the doc obligation. `CHANGELOG.md` and `assets/*/README.md`
  still apply.
- The player-facing word is **nemesis** / **nemeses**. No occult naming in
  game content — no daemon, demon, ghost, wraith or phantom in any authored
  line.
- **No new reward.** Loot and XP already scale with the promoted rarity —
  `progression::kill_xp` prices a kill by challenge, and `Rarity` already
  feeds the drop tables. An achievement, a guaranteed drop or a bonus is a
  magnitude `balance_sim` cannot see, bought for flavour the name and the
  taunt already deliver. Adding one is a scope breach, not an improvement.

### Task 1: The `Nemesis` component and the trigger

The mark and nothing else. Inert until Task 2 gives it teeth, but fully
testable on its own.

**Files:**
- Modify: `crates/engine/src/components.rs` — add `Nemesis`
- Modify: `crates/engine/src/lib.rs:52` — re-export beside `CustomName`
- Modify: `crates/engine/src/tuning.rs` — add `MAX_NEMESES`
- Modify: `crates/engine/src/game/combat_teardown.rs` — the marking pass in
  `end_battle` (`:198`)
- Create: `crates/engine/src/tests/nemesis.rs`
- Modify: `crates/engine/src/tests/mod.rs` — register the module

**Interfaces:**
- Consumes: nothing.
- Produces:
  - `components::Nemesis(pub u32)` — a `Component`, the grudge count.
  - `Game::mark_nemeses(&mut self)` — `pub(crate)`, called from one place.
  - `tuning::MAX_NEMESES: usize = 10`.

**Where the marking pass goes, and why it is a window rather than a
preference.** In `end_battle`, *below* the `StackSpawn` stray sweep and
*above* the `BattleState` removal:

```
  ...
  for stray in strays { self.world.despawn(stray); }   // <- marking goes below this
  <<< mark_nemeses() >>>
  self.world.resource_mut::<MessageLog>().retain_outcomes_since_battle();
  self.world.resource_mut::<BattleTimeline>().frames.clear();
  let lair = self.world.remove_resource::<BattleState>()...  // <- and above this
```

Above the sweep it would mark entities about to be despawned. Below the
`remove_resource` there is no record left of *which* hostiles were in this
fight, only every hostile in the zone.

**The predicate.** `BattleState::groups.is_empty()` is the win, read off the
opponents — a Forgiving defeat is absorbed mid-round by
`difficulty::death_handling_system`, which reboots the player, so their HP
says nothing about the outcome. Non-empty groups means the party walked away
from something still standing, whether carried out or bailed out. Mark every
*living* member of every remaining group. Do not add a `fled: bool`
parameter and do not touch the four `end_battle` call sites.

**The cap.** Count live `Nemesis` holders with a query. At `MAX_NEMESES`, an
entity that *already* has `Nemesis` still increments; an unmarked one is
skipped. No resource, no save field — the entities are the ledger. This
asymmetry is what means there is never a demotion path.

- [ ] **Step 1: Write the failing tests** in `tests/nemesis.rs`. Five, each
      asserting on `world.get::<Nemesis>(e)`:
  - a fight won (groups emptied) marks nobody;
  - a successful jack-out marks the surviving hostile at grudge 1;
  - a Forgiving player death marks the surviving hostile at grudge 1;
  - a second loss to the same program leaves it at grudge 2, not a second
    component;
  - a Stack fight marks nobody, because the `StackSpawn` strays are swept
    first — build it with a `StackSpawn`-tagged pack.

      Fixtures: `tests/support.rs::start_battle_with_a_wild_program` is the
      shape most of these want; look there before writing a new one.
- [ ] **Step 2: Run and confirm they fail** — `cargo test -p
      feral-processes-engine nemesis`. Expect "cannot find type `Nemesis`".
- [ ] **Step 3: Add `Nemesis`, `MAX_NEMESES`, the re-export, and
      `mark_nemeses`; call it from the window above.**
- [ ] **Step 4: Run and confirm they pass.**
- [ ] **Step 5: Write the two cap tests** — an 11th distinct winner is not
      marked; an already-marked nemesis still escalates while the cap is
      full. Confirm they fail, implement the cap, confirm they pass.
- [ ] **Step 6: `cargo fmt`, `cargo clippy --workspace`, `cargo test
      --workspace`, commit.**

### Task 2: Promotion and recharge

**Files:**
- Modify: `crates/engine/src/game/spawning.rs:219-226` — amend the "Rarity
  multiplies here and exactly here" comment to name the second site
- Create or modify: wherever `promote_rarity` best sits —
  `crates/engine/src/game/combat_teardown.rs` beside `mark_nemeses` is
  acceptable; do not put it in `spawning.rs`, which is about entities coming
  into existence
- Modify: `crates/engine/src/tests/nemesis.rs`

**Interfaces:**
- Consumes: `Game::mark_nemeses` from Task 1.
- Produces: `Game::promote_rarity(&mut self, entity: Entity) -> Rarity` —
  `pub(crate)`, returns the tier landed on.

**The formula, because getting this wrong is invisible.** `Rarity` is a
*receipt* for a multiplier already baked into `Stats` at spawn. Applying the
new tier's `stat_mult` would compound. Apply the step:

```rust
let step = new_tier.stat_mult() / old_tier.stat_mult();
// all four of hp, max_hp, atk, def, then write the new tier into `Rarity`
```

- The ceiling is `Rarity::ALL`'s own top. A `Prismatic` nemesis is a no-op
  for stats; only the grudge count rises. **Do not add a
  `MAX_NEMESIS_RARITY` constant** — a second ceiling could disagree with the
  ladder, and the ladder is already bounded at 2.15× cumulative.
- After promotion, `hp = max_hp`. This raises HP, so it stays clear of
  `Game::apply_damage`'s rule about being the only path that lowers it.
- Promotion runs only on a living `Hostile`. Wild programs carry no
  `Equipment`, so the "no stats operation while a gear bonus sits in
  `Stats`" rule is unreachable — pin it with a test rather than a comment.

- [ ] **Step 1: Write the failing tests.** Six:
  - an `Ordinary` nemesis lands on `Silver` with all four stats multiplied
    by exactly `SILVER_STAT_MULT`;
  - a second grudge multiplies by the **ratio** to `Gold` — this test must
    fail if the implementation applies `GOLD_STAT_MULT` to the already-
    promoted stats, so assert the exact expected numbers, not an inequality;
  - a `Prismatic` nemesis does not promote, and its grudge still rises;
  - HP is full after promotion, at the *new* `max_hp`;
  - promotion never runs on an entity carrying `Equipment`;
  - the grudge count and the `Rarity` receipt agree after three losses.
- [ ] **Step 2: Run and confirm they fail.**
- [ ] **Step 3: Implement `promote_rarity` and call it from
      `mark_nemeses`,** in the spec's order: promote, then recharge.
- [ ] **Step 4: Run and confirm they pass.**
- [ ] **Step 5: Amend `spawning.rs`'s comment** so it names
      `promote_rarity` as the one other site rather than claiming rarity
      multiplies in exactly one place.
- [ ] **Step 6: `cargo fmt`, `cargo clippy --workspace`, `cargo test
      --workspace`, plus `cargo test -p feral-processes-engine balance_sim`
      since this moves enemy stats. Commit.**

### Task 4: The name bank and the derived name

**Files:**
- Create: `assets/nemesis/names.ron`
- Create: `assets/nemesis/README.md` — the schema reference
- Create: `crates/engine/src/nemesis.rs` — `NemesisDb` and the seed fold
- Modify: `crates/engine/src/lib.rs` — declare the module
- Modify: `crates/engine/src/game/lifecycle.rs:1257,1325` — load the bank
  and insert it as a resource, beside `DescriptionDb`
- Modify: `crates/engine/src/components.rs:58` — widen `CustomName`'s doc
- Modify: `crates/engine/src/tests/nemesis.rs`

**Interfaces:**
- Consumes: `Game::mark_nemeses` (Task 1), `derive::index`.
- Produces:
  - `nemesis::NemesisDb` — a `Resource` with
    `load_dir(dir: &Path) -> std::io::Result<(Self, Vec<String>)>`, matching
    `DescriptionDb::load_dir`'s signature exactly.
  - `nemesis::name_seed(species: &str, potential: &Potential) -> u64`.
  - `NemesisDb::name(&self, seed: u64) -> Option<&str>`.

**The fold, because reaching the high bits is the caller's problem.**
`derive::index` reads bit 63. One XOR-then-multiply round carries a
difference only ~41 bits upward, so anything folded in as the last word and
differing only in its low bits never reaches the bit that is actually read.
Fold **a byte at a time**, FNV-1a style, the way `sectors::sector_seed`
does and for the same measured reason:

```rust
let mut h = 0xcbf2_9ce4_8422_2325_u64;          // FNV-1a offset basis
for byte in /* every input byte in turn */ {
    h ^= byte as u64;
    h = h.wrapping_mul(0x0000_0100_0000_01b3);   // FNV-1a prime
}
```

Inputs: the species id's bytes and the four `Potential` rolls' `to_le_bytes`.
That makes the name a property of *which program this is*, so two nemeses of
one species differ.

The chosen name is written to the existing `components::CustomName`, once,
on the first mark only — a second grudge must not rename. `CustomName`'s doc
currently says "the player's custom display name" and must be widened to
name this second author, or the next reader will believe `rename_companion`
and `fuse_companions` are the only writers.

Author enough names in `names.ron` that the pool does not obviously repeat —
a couple of dozen. Keep the compiler/process vocabulary the rest of the game
uses, and honour the no-occult-naming rule.

- [ ] **Step 1: Write the failing tests.** Six:
  - marking spends **no** `GameRng` draw — snapshot the resource's state
    across a marking pass and assert it is unchanged. This is what protects
    every arena scenario; it is not a nicety.
  - a name is derived and stored in `CustomName` on the first mark;
  - a second grudge does not rename;
  - two creatures of the same species with different `Potential` rolls get
    different names;
  - a malformed bank file is skipped with a warning and does not panic;
  - with an empty bank, a nemesis is still marked, promoted and recharged,
    just unnamed.
- [ ] **Step 2: Run and confirm they fail.**
- [ ] **Step 3: Write `assets/nemesis/names.ron` and its `README.md`,**
      then `crates/engine/src/nemesis.rs`, then wire the resource in at
      `lifecycle.rs`.
- [ ] **Step 4: Call it from `mark_nemeses`** and run the tests.
- [ ] **Step 5: Widen `CustomName`'s doc comment.**
- [ ] **Step 6: `cargo fmt`, `cargo clippy --workspace`, `cargo test
      --workspace`, commit.**

- Modify: `assets/nemesis/README.md` — document the second bank

- Modify: `crates/engine/src/game/combat.rs:176` — `begin_battle`
- Modify: `crates/engine/src/tests/nemesis.rs`

**Interfaces:**
- Consumes: `NemesisDb`, `nemesis::name_seed` (Task 4).
- Produces: `NemesisDb::taunt(&self, seed: u64, grudges: u32) -> Option<&str>`
  — it folds the grudge count into `seed` itself, so a longer history says
  different things and the fold lives in one place rather than at the call
  site. Fold the grudge byte-wise, the same way `name_seed` folds its
  inputs, for the same high-bit reason.

Fires from `begin_battle` when any hostile in the opening groups carries
`Nemesis`, logged as **`MessageKind::Info`**. `Info` is deliberate:
`MessageLog::retain_outcomes_since_battle` keeps only `Outcome`, `Loot`,
`LevelUp`, `Raid` and `Complete`, so the taunt is pruned when the fight ends
and does not follow the player onto the map. `game/taunt.rs` is the pattern
to match, including its doc comment's reasoning.

Author lines that read as a program with a history — referencing having sent
you away before, without assuming *which* way it happened, since a defeat
and a jack-out share the trigger.

- [ ] **Step 1: Write the failing tests.** Four: a battle opened against a
      nemesis logs a taunt; a battle against an unmarked program logs none;
      the line is `Info` kind and is gone from the log after `end_battle`;
      a higher grudge count selects a different line.

### Task 6: The map

**Files:**
- Modify: `crates/engine/src/views.rs:406-537` — `EntityView` gains
  `nemesis: bool`; amend the `rarity` field's doc, which currently records
  the rule this task breaks
- Modify: `crates/engine/src/game/inspection.rs:341` (`build_views`, the
  `difficulty_color` call at `:449`) and `:1021` (`difficulty_color` itself)
- Modify: `crates/gui/src/render/base.rs:820-840` — the tile mark, and the
  comment there claiming the con read "cannot be given up"
- Modify: `crates/engine/src/tests/nemesis.rs`, plus a gui render test

**Interfaces:**
- Consumes: `components::Nemesis` (Task 1).
- Produces: `views::EntityView::nemesis: bool`.

Two marks, both wanted:

1. **A distinct tile mark** in `base.rs`, alongside the rarity bar already
   drawn along the tile's top edge. Its exact form is a rendering call —
   constrained only to not collide with that bar or with the outlines drawn
   for a structure's production links.
2. **A reserved glyph colour** from `difficulty_color`, returned regardless
   of power ratio. Give it a fourth parameter rather than a second function;
   the existing `is_boss` always-magenta override is the precedent for a
   non-power reading winning the glyph.

**A boss can also be a nemesis, and nemesis wins.** Check it *before*
`is_boss`. Being a boss is a fact about how the thing spawned; being a
nemesis is a fact about what it did to you, which is both more specific and
the one you can act on. Pin the precedence with a test so it cannot flip
silently when someone reorders the branches.

**The species glyph character does not change.** It is the only thing on the
tile saying *what* the nemesis is.

**Both doc comments this breaks must be amended, not left lying.**
`EntityView::rarity`'s doc and `base.rs`'s block comment both state that the
glyph's colour is reserved for `difficulty_color` because it can hold only
one reading. That rule is now conditional, and the spec's "what the recolour
costs" section is the argument to carry across.

- [ ] **Step 1: Write the failing tests.** Four: `EntityView::nemesis` is
      true for a marked hostile and false otherwise; `difficulty_color`
      returns the nemesis colour regardless of power ratio; a boss that is
      also a nemesis draws the **nemesis** colour, not magenta; a breach
      clears every nemesis.
- [ ] **Step 2: Run and confirm they fail.**
- [ ] **Step 3: Add the view field, the `difficulty_color` parameter and
      the call-site wiring.**
- [ ] **Step 4: Run and confirm they pass.**
- [ ] **Step 5: Draw the tile mark in `base.rs`** and add a gui test in the
      style of the existing `render/` tests. `paint::with_painter` measures

- [ ] **Step 6: Amend both doc comments.**

- Modify: `docs/seams.md` — the argument for each new seam

The seams worth recording, each one line in `CLAUDE.md` and its argument in
`docs/seams.md`:

- **A nemesis is marked by the one predicate that already decides a win**,
  `groups.is_empty()` inside `end_battle`, so a defeat and a jack-out are
  the same fact and no call site knows about it. Its position in
  `end_battle` is a window: below the `StackSpawn` sweep, above the
  `BattleState` removal.
- **Rarity's multiplier now touches `Stats` at two sites, not one.**
  `spawn_wild_creature_scaled` bakes the tier in; `promote_rarity` applies
  the *ratio*. Applying the tier compounds invisibly on every reload.
- **The nemesis ladder is bounded by `Rarity::ALL` itself** — 2.15×
  cumulative, decelerating — which is why it does not violate the
  linear-difficulty-curve rule and why there is no second ceiling constant.
- **Nothing in this feature draws from `GameRng`**, because `end_battle`
  runs in every arena fight and a draw would shift every scenario's stream.
- **The glyph's colour is no longer reserved for `difficulty_color` alone.**
  A nemesis wins it, and the con read is spent on that tile.

## Playtest before this is called done

A green suite is not evidence this feels like anything, and this repo has a
standing record of features shipping unplayed. Two questions only play
answers:

- **Is +50% on the first promotion the right size?** It is the largest step
  on the ladder and it lands on a player who just lost.
- **Does the map read?** A nemesis mark, a rarity bar and a reserved glyph
  colour is three things on one tile, and the con read is gone.

`cargo run` and lose a fight on purpose. Then
`cargo run --bin savetool -- capture saves/save.bin nemesis` so the second
question never again costs a lost fight to ask.

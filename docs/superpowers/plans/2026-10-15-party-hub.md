# Party hub Implementation Plan

> **For agentic workers:** use superpowers:subagent-driven-development, with one subagent per phase. Steps use checkbox (`- [ ]`) syntax.

**Goal:** `p` opens a third hub, titled PARTY, with the pages Companions (the roster), Programs, Routines and Perks. The party menu is deleted.

**Spec:** `docs/superpowers/specs/2026-10-15-party-hub-design.md`. Read it first; this plan does not restate it. The **Reachability** table there is the acceptance list.

## Why phases

The hub machinery (`Hub`, `HubPage`, `hub_of`, `handle_hub_nav`, `hub_last`, the gui frame) is already generic since the inventory hub, so there is no refactor phase. Phase 1 is app-core only, Phase 2 is gui only, so neither subagent loads the other crate. Phase 1 leaves the gui drawing the four party modes through its existing popups, so the tree stays green between phases.

## Global constraints (every phase prompt carries these)

- No engine, schema or save change.
- Only `crates/gui/src/paint.rs` names a graphics library (`.claude/rules/drawing-seam.md`). Read `.claude/rules/seams-screens.md` before editing. `command_rows` stays the only source of a command page's rows.
- Follow existing naming; comments say why. Delete what becomes unused (`Mode::PartyMenu`, `PARTY_ROWS`, `party_menu_rows`, `handle_party_menu_key`, the roster and Perks handlers' Esc arms, the party-menu `draw_group_menu` arm). No shims or aliases.
- Uppercase letters are actions, lowercase are row selectors. Every existing letter shortcut keeps working.
- Gates per phase: `cargo fmt`, `cargo clippy --workspace --all-targets` clean, the phase's crate tests. **Unset `FERAL_DEV_NO_SIEGES`** first. Don't pipe cargo when the exit code matters.
- Git: branch `party-hub` off `main` in the primary checkout (the spec commit `7a06aefd` is already on `main`). Commit at each green step, explicit paths only (never `git add -A`). Never push; never run `git checkout`, `stash` or `reset`.
- Docs: never touch the manual, README or TODO.md. CHANGELOG is written at release.

## Phase 1: party hub behaviour (app-core, TDD)

**Files**

**Perks previews (decide in this phase).** `open_perks` is the single writer of `perk_previews`. A rail turn, `[`/`]` or `p` reopening on Perks sets `self.mode` without calling it. Pick **one** place that refreshes on every entry to `Mode::Perks`. The recommended place is the hub bookkeeping in `input.rs`, which already runs on any hub-mode transition: refresh when `before != Mode::Perks && after == Mode::Perks`. Then reduce `open_perks` to whatever is left, or delete it if nothing is. Keep the field doc's "one writer" claim true and point it at the place you chose. The test asserts the previews are fresh after a rail turn, not just after LevelUp `P`.

**Steps** (each red → green → commit)
- [ ] Hub shape: test that `p` opens on Companions with the cursor on the rail; Down/Up wrap across the four pages; `[`/`]` turn; Right/Enter go into the page; Esc goes to the rail and then to the map; `p` reopens on the last page; the `b`, `i` and `p` slots are independent; the existing "no mode in two hubs" test now iterates three hubs.
- [ ] Command pages: rows come from `command_rows` and match the old `PARTY_ROWS` availability. Use a save with one companion and no fusion research, so Fuse is hidden and the page still turns and Esc's. Selecting a row sets `menu_origin` to the page.
- [ ] Reachability: one test per **test** row of the spec's table, driven through `handle_key` from `p`. Assert the landing mode, `hub_on_rail == false` on returns, and the kept `menu_selected` where the spec says "same row". Cover the etch `[e]` detour's two Esc paths.
- [ ] Perks: LevelUp `P` lands on Perks in the page. Previews are fresh after a rail turn: change perk state, turn away and back, and compare against `Game` directly. PerkBought, AllocateStats and the respec confirm return to Perks in the page with the row kept.
- [ ] Delete `PartyMenu` and the dead code. Run `rg "PartyMenu|PARTY_ROWS|party_menu" crates/` and get zero hits. Check every `"party menu"` string hit in `crates/` against the spec. Gui will fail to compile on the deleted mode: in this phase, change only the gui match arms needed to compile, sending `PartyPrograms`/`PartyRoutines` wherever `BaseBuild` goes. Phase 2 does the drawing.
- [ ] Gate: `cargo test -p feral-processes-app-core`, then `cargo build -p feral-processes-gui`.

**Handback:** commits, where the Perks refresh lives, any test that needed more than a mechanical port and why.

# Sites Hub Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One hub, opened with `w` at base or beside a site, that lists every known town, city and outpost plus a Caravans entry. Each entry has status, goods (last seen, or live after research), routes, jobs, crew and a per-site log, and the hub gathers every action the rules already allow from where the party stands.

**Architecture:** Phase 1 moves the hub framework onto ADR 0043. A rail is owned runtime data (`HubPage` with a key, a `String` title, a glyph, a section and its `!`), and the page being shown is held in `App` by key and checked against the `Mode`. All four existing hubs migrate with no visible change. Phase 2 adds an engine `sites/` subsystem: a per-site log and a last-seen shelf held as plain Rust on `Game` (ADR 0042's precedent), one time-banding helper, and the views. On top of that sit an app-core `Hub::Sites` with ten tab modes, gui pages in the hub frame, a research node that turns on the live shelf, and the removal of Dispatch's route-destination section.

**Tech Stack:** Rust workspace, bevy_ecs (engine), bevy + egui (gui).

**Spec:** `docs/superpowers/specs/2026-11-06-sites-hub-design.md`. **ADR:** `docs/adr/0043-a-hub-rail-is-runtime-data-and-its-page-is-held.md` (Agreed). **Mockup** (layout only): https://claude.ai/artifact/EaLKiWom6so1hWdwa9Uym2. Read the spec and the ADR before Task 1.

## Global Constraints

- The renderer never touches `World`. Every figure and every sentence on the Sites pages comes from an engine view, and gui only lays it out. app-core owns row counts, and both sides call the same engine function.
- **No tick numbers reach the player.** Every age and wait on the Sites pages goes through `sites::time_band`. Reusing `OutpostReport::route` or `outpost_route_line` here is forbidden, because they carry ticks.
- No new remote gameplay doors. Every action calls an existing engine door, which refuses in its own words, and the refusal goes through `App::refuse`. An action that isn't available is still drawn, and it is refused when used.
- Lists are highlight + Enter, with no row digits. Hub nav goes through `App::handle_hub_nav` only. A screen that keeps an arrow or `Esc` registers in `App::screen_claims`. A read-only page never advances the game.
- No `match hub` outside `Hub::kind`. Hub identity lives in its `HubKind` impl, and gui names no hub.
- Save additions are `#[serde(default)]` with **no `SAVE_FORMAT_VERSION` bump**. Each gets a real `Game::save` → `Game::load` test.
- New engine state is plain Rust on `Game`, never a `Resource` (ADR 0042: a resource shifts query order). Constants go in `crates/engine/src/tuning/settlements.rs`. RNG is untouched: no new `GameRng` draws, and no reordering of existing ones.
- Plain language, no occult naming, no slogans. Key hints use the handler's own case.
- Text never clips or wraps. Every new rail title, row and log line has a width census at 1280x720.
- `cargo fmt`, then `cargo clippy --workspace --all-targets` clean, then `cargo test --workspace` green. Unset `FERAL_DEV_NO_SIEGES` before testing. `balance_sim` runs only if a balance constant in `tuning/` moves (none should).
- Git: commit at each green step with explicit paths. Never `git add -A`/`.`, never `git checkout`/`stash`/`reset`, never push. The CHANGELOG is not edited on the branch.

## Review Focus

1. **A screen entered by setting `mode` directly** (map `D` → Downed programs, `N` → Alerts, Overview Enter, a sub-screen's `close_screen` back onto a hub page, level-up `p` → Perks) must still draw in its hub frame and answer `hub_at`. These are pinned by the Task 1 census and by `settle_hub` tests in Task 2.
2. **Esc from a launched site screen** (market, board, post picker, outpost take, route cargo) returns to the exact Sites tab and site it came from, with the cursor in the page, even when other sites share that tab's mode. Tested in Task 10.
3. **A site leaving the rail while it is held.** An outpost destroyed or a save loaded with a held key: reopen falls back to the first page, and nothing panics on a missing key. Tested in Tasks 2 and 9.
4. **Two sites with one name, and a very long modded name.** The rail stays ordered and unique by key, and the title is elided with its `!` kept. Tested in Tasks 3 and 12.
5. **Hub opened beside a site that is also next to the base floor.** The beside-site actions are enabled for that site only, and the base actions still work. Tested in Task 9 (`site_reach` precedence) and Task 10.

`settle_hub` resolves this algorithm, which the tests don't fully determine. Let `shown = base_popup_parent(mode).unwrap_or(mode)`.
1. If `mode` is `Playing` or `MainMenu`, clear `hub_place`.
2. Else, if the held page offers `shown`, keep it.
3. Else, if another page of the *held* hub offers `shown`, re-key to the first such page. This covers the Overview jump, sub-screen returns and Left/Right between screens.
4. Else, if exactly one page across all `Hub::ALL` (from each `kind.pages(self)`) offers `shown`, adopt it. This covers map `D`/`N` and other direct entries.
5. Else leave the held place untouched. The mode is outside the hub (a launched screen), and `hub_at` answers `None` until it comes back.

The uniqueness test in step 4 keeps a mode shared by many pages (Task 9's Sites tabs) from ever being adopted by guess. `handle_hub_nav` and `open_hub` set `hub_place` before calling `kind.turn`, because a turn that closes the hub (structure page opener failing) is then cleared by step 1. `open_hub` restores `hub_last` only when its key is still on the rail and its mode is on that page, and otherwise turns to page 0.

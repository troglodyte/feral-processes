# Hub Merge, Named Tabs and Mouse — Implementation Plan

> **For agentic workers:** use superpowers:subagent-driven-development or
> superpowers:executing-plans. One phase per session: `/clear` between phases,
> and each phase ends in a release (`skills:deploy`). Steps are `- [ ]`.

**Spec:** `docs/superpowers/specs/2026-11-09-hub-merge-design.md`.
**ADRs:** 0045 (hubs and nav) and 0046 (pointer layer), both Agreed. 0043
(rail is runtime data, page held by key) still holds. **Mockup:**
https://claude.ai/artifact/C55zQrJ26S9kwVMaMGoDiX (layout only).

**Architecture:** layered as today. The engine facade `Game` gains nothing new
except what a view needs. app-core owns the hubs: `HubKind` impls, runtime rail
data and the one nav dispatcher, `App::handle_hub_nav`. gui draws in immediate
mode. Phase 1 adds named tabs and the Tab/Shift+Tab rule. Phases 2 and 3
regroup the `b` and `i` rails. Phases 4 and 5 add a pointer layer: targets are
registered while drawing, and every hit is turned into the key it stands for.

## Global constraints

- app-core owns row counts and what a key or click means. gui has no
  `match app.mode` for behaviour and names no hub. `Painter` stays the only
  file that names a graphics library.
- One nav rule for every hub (`handle_hub_nav`). A page takes keys back only
  through `screen_claims`. The rail is `HubKind::pages` only. There is no
  `match hub` outside `Hub::kind`.
- `Row::Item` ordinal == app-core selection index on every hub tab.
- Text never clips. Every new string (tab strips, rail titles and sections,
  rows) goes under a 1280×720 width census.
- No new remote gameplay. Every action calls its existing door, and a refusal
  goes through `App::refuse` in that door's words.
- Nothing is saved, so there is no save change and no `SAVE_FORMAT_VERSION`
  bump. No RNG, `tuning/` or balance change, so `balance_sim` is not needed.
- Lists are highlight + Enter. Key hints use the handler's case. Plain
  language.
- Gates after every task: `cargo fmt`, then
  `cargo clippy --workspace --all-targets` clean. Each phase ends with
  `cargo test --workspace` green (unset `FERAL_DEV_NO_SIEGES` first).
- Git: commit at each green step, staging explicit paths. Never `git add -A`,
  `checkout`, `stash`, `reset` or push. CHANGELOG and version bumps happen at
  deploy, not on the branch.
- Do not edit `assets/help` or the manual. Do sweep old-path text
  (`b → Trade`, `w` as its own hub) in `assets/` and in key hints, in the
  phase that moves the page.
- Seam docs: update `seams-screens.md` / `drawing-seam.md`, the `seams`
  skill and the `seam:` graph entry in the phase that changes each one, in
  the order the skill documents.

## Decisions this plan makes (from the spec's "Calls" and builder slots)

1. **The spec contradicts itself on the structure hub in phase 1.** The later
   "Calls" section wins: phase 1 leaves `c`'s `Tab` cycle alone, and phase 3
   deletes it. In phase 1 the structure hub's `HubKind::key` also claims
   `ShiftTab`, as the previous structure, so `Shift+Tab` is not
   half-adopted there.
2. **Tab names live beside the mode:**
   `pub struct HubTab { pub name: &'static str, pub mode: Mode }`, and
   `HubPage::tabs: &'static [HubTab]` replaces `screens`. `FixedPage` gets
   the same field. `TOWN_TABS` and `OUTPOST_TABS` become `HubTab` tables.
3. **Within a hub, `Tab` belongs to the hub.** `toggle_manifest_tab` moves
   to `←/→`, claimed in `screen_claims`: `→` steps toward the last face, and
   `←` off the first face goes back to the rail. This happens only when
   `Mode::Manifest` is shown as a hub tab (`hub_at().is_some()`). Off-hub
   (the map's manifest) it keeps `Tab`, because the hub rule is not running
   there, so neither key has a second meaning. Check `social_tab.rs` stays
   green, and add hub-side cases.
4. **Popup-only targets** (the Research pickers, Compile, Caravan, Dispatch,
   Contracts). Where the screen's renderer can draw into a given content
   `Rect`, it becomes a tab in the frame. Otherwise it opens over the hub and
   owns Esc/Tab through `screen_claims` until it closes. Record which, per
   screen, in the phase's commit message.
5. **Structure verb keys on Info:** `W` (work it), `U` (upgrade) and `X`
   (demolish), only if the key-hint census and the existing Info bindings
   leave them free. Otherwise pick the next free letters and record them.
   Hold stays on the Hold tab.
6. **Hover tint:** `palette::SELECT_BG` at about 40% alpha, as a new named
   constant `HOVER_BG` in `hud/palette.rs`.

## Phase 1 — Nav rule and named tabs (release)

No rail changes. The goal is that every hub but `c` walks the new rule and
draws named tabs.

**Files:** `crates/app-core/src/lib.rs` (`GameKey::ShiftTab`, and its name
in the key-names list), `app/hub.rs`, `app/base_report.rs`,
`app/inventory_hub.rs`, `app/game_menu.rs`, `app/sites_hub.rs`,
`app/structure_hub.rs` (`HubTab` tables only, plus decision 1),
`app/inspection.rs` (decision 3), `crates/gui/src/lib.rs` (map Shift+Tab →
`ShiftTab`, before the plain `Tab` arm),
`gui/src/render/base_report/frame.rs`, every renderer that reads
`.screens`. Tests: `app-core/src/tests/hub_census.rs`, a new
`tests/hub_nav.rs`, the `Tab`-using cases in `tests/base_report.rs`, and
`gui/src/render/tests/` (strip census).

- [ ] **1.1 Rename to tabs.** Replace `screens: &'static [Mode]` with
  `tabs: &'static [HubTab]` across `HubPage`/`FixedPage` and every table.
  Name each tab from the spec's tables, or from today's screen titles where
  the page is not regrouped. `hub_at`'s third element is now the tab index.
  This is a mechanical step with no behaviour change, so the existing suite
  is its gate. Commit.
- [ ] **1.2 Nav rule, test first** (`tests/hub_nav.rs`). For every hub except
  Structure, on the rail and in the page:
  - `Tab` and `ShiftTab` cycle the highlighted page's tabs, wrapping at the
    ends and staying in the same half.
  - `Right` in a page no longer changes tabs.
  - `Left` from the leftmost position goes back to the rail on every tab.
  - `{ }` jumps to the first page of the next/previous `section`, wrapping.
    On a hub with no sections they are a no-op.
  - `{ }` yields to an applied or active text filter.
  - On Duties, `←/→` never switch tabs, at any column.
  - On a level row, `←/→` are the row's.

  Then change `handle_hub_nav`. `Left` no longer steps to the previous
  screen. `ShiftTab` and `{ }` are added. A filter claiming `Char` goes in
  `screen_claims`.
- [ ] **1.3 Manifest toggle** (decision 3). Test: inside `i` → Manifests,
  `Tab` switches the hub tab and `→` switches the manifest face. The map
  manifest still takes `Tab`.
- [ ] **1.4 Tab strip.** `draw_title` draws `Title   One · [Two] · Three`,
  with the current tab in `SELECT_BG`/`PANE_TITLE`. Write a pure
  `fn tab_strip_fits(…) -> bool` (measure only, so it can be unit-tested) and
  fall back to today's dots when it is false. Census: every page of every
  hub at 1280×720, with the pages that fall back listed as an expected
  literal. Use the `popup_row_width` headless precedent.
- [ ] **1.5 Keybar.** Use `[ ] page`, `Tab tab` and `{ } section`, and drop
  `←/→ screen`. Pin the wording with a keybar test.
- [ ] **1.6 Seams and docs.** Update the hub rule sentence in
  `seams-screens.md`, the skill and `seam:` for `Tab`/`ShiftTab`/`{ }`. Then
  the full suite.

## Phase 4 — Pointer layer and hub mouse (release)

**Files:**
- Create `crates/gui/src/pointer.rs`, the only reader of egui pointer
  input.
- Move `PointerHit` from `app/sprite_editor.rs` to `app/pointer.rs` (which
  already holds the map's `set_map_hover`) and widen it.
- `gui/src/paint.rs` (`target`), `gui/src/render/base_report/frame.rs`
  (registration), `gui/src/lib.rs` (wire the reader),
  `gui/src/render/hud/palette.rs` (`HOVER_BG`).

**Interfaces:**
```text
app-core  enum PointerHit { Cell(..), Swatch(..), Button(..), Subject(..),   // existing
                            Page(HubPageKey), Tab(usize), Row(usize),
                            Key(GameKey), More(Direction), MapTile(i32, i32) }
          struct PointerEvent { hover: Option<PointerHit>, press, drag, up,
                                double: bool, button: PointerButton, wheel: i32 }
          App::handle_pointer(&mut self, PointerEvent)
          App::pointer_hover: Option<PointerHit>      // replaces map_hover in phase 5
          App::hovered(&self, &PointerHit) -> bool
gui       Painter::target(&self, rect: Rect, hit: PointerHit)   // local Rect
          pointer::Reader { prev: Vec<(Rect, PointerHit)>, armed: bool, .. }
          Reader::frame(&mut self, ctx: &egui::Context, app: &mut App)
```

- [ ] **4.1 The app-core half, test first.** Each hit is the key it stands
  for:
  - `Page` turns the rail and focuses it;
  - `Tab(i)` switches tab;
  - `Row(i)` selects the row, and selecting it again or double-clicking is
    `Enter`;
  - `Key(k)` is `handle_key(k)`;
  - `More` scrolls;
  - the wheel is `↑/↓` on the hovered region.

  Tests assert each one equals its key path on a hub page.
- [ ] **4.2 The gui half.** `target()` records to a per-frame list owned by
  the reader, not global state. The reader resolves hits against the
  previous frame's list, owns "armed" (a button already held when a screen
  opens does nothing) and click-vs-drag, and reads the wheel from
  `smooth_scroll_delta`. Test with headless egui frames, as the existing
  `handle_map_pointer` tests do: hover follows the previous frame, an
  unarmed press does nothing, a double-click is Enter, a keycap click equals
  its key, and the wheel equals `↑/↓`.
- [ ] **4.3 Register in the hub frame:** rail entries, tab-strip names, item
  rows (`Row::Item` ordinal only), keybar keycaps and the "↑/↓ n more"
  markers. Draw hover from `app.hovered`. Census: on every hub tab, the
  registered row ordinals equal app-core's selection range.
- [ ] **4.4 Docs.** Add the target rule to `drawing-seam.md`, then the
  skill, then `seam:`. Then the full suite.

## Review focus (final opus review, whole branch)

1. Every screen entered by setting `mode` directly still answers `hub_at` on
   the right page after the regroup. That covers map `D` → Downed, `N` →
   Alerts, level-up `p` → Perks, Overview Enter, and every `close_screen`
   back onto a merged tab. Use `shared_screens_are_pinned`.
2. `Tab` is never spent twice. Inside a hub it belongs to the hub. Popups
   over a hub own it until they close. Off-hub screens are unchanged.
3. A held page vanishing (demolish, delivery, outpost lost, a member
   leaving) never panics and lands on the rule's page.
4. The town Jobs tab and Contracts → Held are one contract, and both
   abandon paths go through one door.
5. The pointer can't do anything a key can't: no `match app.mode` in
   `gui/src/pointer.rs`, and every `PointerHit` arm ends in an existing key
   path.
